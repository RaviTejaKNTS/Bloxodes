# Scripts Guide

Scope: `scripts/`.

These files are operational jobs, imports, backfills, collectors, and automation workers. Many are side-effectful.

## Default Rules

- Prefer the stable `package.json` alias when one exists.
- Keep shared helpers in `scripts/shared/`.
- Group new scripts by task area instead of adding everything at the top level.
- Document required env vars and downstream side effects when introducing a new script.
- For script env loading, use `scripts/shared/load-env.ts`. Profiles and overlays are defined in `env/config.json`; do not add root `.env*` fallbacks.
- When a script changes pipeline behavior, schedules, env ownership, or side effects, update the existing owning `dev-docs/pipelines/*`, `dev-docs/environment.md`, or operations page in the same change; do not create a parallel current-state doc.

## Folder Map

- `dev/`: workstation development and worktree setup.
  - `setup-worktree.sh` powers `npm run setup:worktree`. In linked worktrees only, it links ignored `.envs/` from the main checkout without overwriting an existing path, installs dependencies when `package-lock.json` changes, and creates ignored temp/report directories.
  - `start-managed-dev.ts` powers both `npm run dev` and `npm run dev:managed`. It loads `.envs/targets/managed-dev.env` and refuses targets outside HTTPS `*.supabase.co`.
  - `env-doctor.ts` owns workstation readiness and safety checks; `check-env-contract.ts` owns committed example coverage. The one-time legacy env migration commands are retired.
  - `check-migration-integrity.ts` validates migration filenames, version uniqueness, the convergence policy, seed retirement, and future `SECURITY DEFINER` search paths without connecting to a database.
  - `check-managed-dev-readiness.ts` is a read-only managed-development schema/API check. It must retain the managed-project URL guard.
  - There is no active local Supabase target, local seed/reset workflow, or local-key sync command.
- `ops/`: platform health and deliberately gated synchronization.
  - `check-platform-sync.ts` compares the local checkout, cached `origin/production`, public production SHA/database health, homelab checkout/timer, VPS web image, and production migration ledger. It is read-only; use `--local-only` before a release and the full check after approved synchronization.
  - `release-production-schema.ts` plans by default by streaming one transaction through SSH into the existing `supabase-db` container and rolling it back. `--apply` additionally requires the exact released `origin/production` SHA and `--confirm "APPLY production"`; it proves objects, repairs only policy-listed history, applies only expected pending migrations, commits atomically, and verifies the ledger. Never run apply without explicit production permission. Do not enable SSH forwarding or expose Postgres for this workflow.
  - `release-production-edge-function.ts` compares a checked-in function with the self-hosted Edge Runtime mount and is read-only by default. Apply requires the exact released SHA plus `--confirm "APPLY <function>"`; it stages by SSH, installs through the root container mount while preserving host ownership/mode, restarts only Edge Runtime, performs an authenticated smoke call, and rolls back on failure.
  - `sync-homelab-checkout.sh` requires an exact full SHA and is dry-run by default. `--apply` is a remote mutation and requires explicit production/synchronization approval. Its post-fast-forward readiness check loads `/etc/bloxodes/article-automation.env` through Node's env-file support, matching the systemd runtime without printing values.
  - `install-homelab-article-automation.sh` requires `--apply <approved-full-sha>` and preserves the timer state. Never install units from an uncommitted or unapproved checkout.
  - `sql/verify-production-history-repair.sql` proves the four audited pre-convergence production objects before the production release command marks their missing ledger versions applied. Keep it synchronized with `supabase/migration-policy.json`; history repair is a production mutation and requires explicit approval. `20260628000100` is a real pending view migration and must execute normally.
- `quality/`: final-stage content checks, post-publish URL verification, and manual sitemap/SEO/route/render diagnostics. E2E release reuses completed final checks and must not rerun the suite. Agents may use deeper audits while troubleshooting when their expected time and shared VPS/origin load are proportionate; start with the narrowest useful command. Use `verify:published-url` after one database page is published. See `docs/testing/stability-and-seo.md`.
- `ads/`: build-time ad and policy helpers.
  - `audit-journey-catalog-dom.ts` is the read-only local DOM guard for every Music IDs and Decal IDs route shape. Start the local web app, then run `npm run audit:journey-dom -- --base-url http://127.0.0.1:<port>`; it requires exactly one `#article-body`, direct block-level `data-journey-item` children, and no manual Mediavine content hints.
  - `audit-journey-catalog-browser.ts` verifies the hydrated content stream at desktop and mobile widths and inserts a synthetic direct child to prove an in-content placement spans the full lane. Run `npm run audit:journey-browser -- --base-url http://127.0.0.1:<port>`.
- `articles/`: article generation and article refresh.
- `automation/`: queue runners, IndexNow/bootstrap helpers, Google Indexing API submitter, cache warming, reporting.
- `catalog/collect-roblox-font-ids.ts` reads the complete official Creator Store FontFamily set, face manifests, and thumbnails. It is dry-run by default; `--apply` writes managed development, and writes elsewhere additionally require `--allow-prod`.
- `catalog/collect-roblox-mesh-ids.ts` reads the current 1,000-result public Creator Store MeshPart selection, stores each wrapper asset with its underlying Mesh ID and optional Texture ID, and fetches square Roblox thumbnails. It is dry-run by default; `--apply` writes managed development, and writes elsewhere additionally require `--allow-prod`.
- `catalog/sync-game-specific-id-sources.ts` refreshes the committed source-backed associations for game-specific Music IDs and Decal IDs pages. Review `data/game-specific-ids/source-backed.json` after every run; source association does not imply an in-game playback or image-input test.
- `catalog/seed-game-specific-id-usage.ts` upserts that reviewed dataset into the game-usage tables. Use `npm run seed:game-specific-id-usage -- --dry-run` first; add `--replace-source-rows` only when the committed file should replace rows owned by the same game/source pairs. It refuses targets outside managed development unless `--allow-prod` is explicit.
  - `google-indexing-submit.ts` is a guarded Google Indexing API job. It loads `.envs/pipelines/indexing.env`, requires `--apply` plus `GOOGLE_INDEXING_API_ENABLED=true`, and should use Supabase state in recurring production runs.
  - `warm-cloudflare-cache.mjs` is an explicit manual cache-warming tool. It is not part of the daily deployment path. Default `CACHE_WARM_MODE=deploy` warms the sitemap files, main/index/legal pages, all wiki/catalog/tool URLs, and a recent slice from DB-backed detail sitemaps. Use `CACHE_WARM_MODE=full` only for an intentional full-site warm. Use `CACHE_WARM_DRY_RUN=true` to inspect selection without page requests. Do not send cache-bypass request headers because the goal is to fill Cloudflare.
  - `cloudflare-emergency-cache.mjs` toggles a temporary Cloudflare Cache Rule for anonymous public HTML when origin/Supabase is unhealthy. It uses the local operator token `CLOUDFLARE_BLOXODES_API`, not the runtime purge token. Use `npm run cloudflare:emergency-cache:status`, `npm run cloudflare:emergency-cache:on`, and `npm run cloudflare:emergency-cache:off`; keep it off during normal operations.
  - `audit-sitemap-seo.ts` crawls the sitemap index, checks each page response, and writes SEO/indexability reports to `tmp/seo-audits/`. It is read-only, uses live HTTP requests only, and can be limited with `npm run audit:seo -- --limit 100` for smoke tests.
  - `audit-html-size.ts` measures uncompressed HTML bytes for explicit URLs or sitemap URLs and writes reports to `tmp/html-size-audits/`. Use `npm run audit:html-size -- --url <url> --fail-on-limit` as a pre-publish guard for large catalog pages; add `--rewrite-origin https://bloxodes.com http://127.0.0.1:<port>` when testing a production sitemap against localhost.
  - `enqueue-revalidation-events.ts` inserts coalesced rows into `revalidation_events` for the Supabase revalidation worker. Use `npm run enqueue:revalidation -- --event stats:stats --event stats:games --event stats:creators --event stats:items` for script/workflow-driven events that should follow the same queue as table triggers.
  - Revalidation events are drained by the VPS Supabase `revalidate` Edge Function every minute. Do not warm Cloudflare synchronously from scripts; `/api/revalidate` queues `cache_warm_events`, and the VPS `cache-warm` Edge Function warms URLs separately.
- `backfill/`: repair jobs for existing content/data.
  - `repair-legacy-supabase-media.ts` inventories published `code_pages` and `articles` for non-canonical Supabase Storage URLs on either the retired managed origin or `database.bloxodes.com`. It is read-only by default, requires `--allow-remote-read` for a remote audit, and requires both `--apply` and `--allow-prod` for production changes. Recovered object bytes must be staged beneath `--recovery-root` as `<object-path>/<physical-version-file>`; uploads go through the supported Storage API before rows are updated. Optional flags explicitly replace missing codes covers from official Roblox thumbnails or remove only unrecoverable Markdown image tokens. All current writers must store public Storage URLs on `https://media.bloxodes.com`; `storage-public-url.ts` canonicalizes both non-canonical origins as a fallback when an automation environment omits `SUPABASE_MEDIA_PUBLIC_URL`.
- `catalog/`: site-wide Roblox item and bundle collection plus enrichment.
  - `refresh-roblox-promo-rewards.ts` validates the complete RobloxDen promo list, stores only structured source facts, distinguishes assets from bundles through official Roblox metadata, uses the matching official thumbnail endpoint, and updates `roblox_promo_rewards`. It is dry-run by default; writes require `--apply`, and targets outside managed development additionally require `--allow-prod`. Missing rewards are retired only after two complete-source misses by default (`ROBLOX_PROMO_RETIRE_AFTER_MISSES` or `--retire-after-misses` can raise the threshold). Incomplete or empty source responses never change miss counters. Apply uses one advisory-locked transactional RPC, audits through `stats_job_runs`, and changes `catalog_pages.updated_at` only when material reward data changes. `ROBLOX_PROMO_CONCURRENCY` and `ROBLOX_PROMO_MAX_RETRIES` tune official Roblox requests.
  - Broad Roblox Marketplace collectors write to `roblox_catalog_items` and enqueue `roblox_catalog_refresh_queue`. Use `npm run collect:catalog-items` for accessories, body, clothing, avatar animations, and makeup. Production discovery must set `ROBLOX_CATALOG_MAX_QUERIES`, `ROBLOX_CATALOG_MAX_PAGES`, and a rotating `ROBLOX_CATALOG_ROTATION_OFFSET` (the orchestrator derives one from `ROBLOX_CATALOG_ROTATION_WINDOW_HOURS`) so one run cannot expand into hundreds of throttled requests and successive runs cover different subcategory/sort/keyword slices. The orchestrator expires discovery audit rows left running for more than two hours before starting a new pass. Friendly sort labels must pass through `robloxCatalogSortParams`; Roblox silently ignores string `SortType` values and requires numeric values `0` through `5` plus all-time aggregation for favorite/sales sorts. The live Roblox catalog search API only accepts `limit` values `10`, `28`, or `30`; keep collectors clamped to those values. Bundle-returning categories such as full bodies, shoes, and animation bundles must preserve `item_type = 'Bundle'` so the enrichment job can request bundle thumbnails.
  - `collect-roblox-makeup-items.ts` discovers Makeup items through keyword searches and filters asset type IDs `76`, `77`, `88`, `89`, and `90`, because Makeup is not exposed in the normal category list.
  - `enrich-roblox-catalog-items.ts` refreshes metadata/history and caches thumbnails. It must call the asset thumbnail endpoint for assets and the bundle thumbnail endpoint for bundles.
  - `collect-roblox-free-items.ts` merges zero-price candidates from the official Roblox catalog search with source-tagged rows already stored in `roblox_catalog_items` (including RobloxDen imports) and previously verified rows. Candidate provenance is discovery-only: every displayed row must still pass a current Roblox asset/bundle API claimability check. The collector stores verification fields and matching thumbnails, is dry-run by default, and supports `--skip-stored-candidates`, `--skip-previously-verified-candidates`, and `--skip-live-search` for narrow/resilient diagnostics. A skipped/partial search never retires unseen rows. Use `npm run collect:free-items -- --apply` for local writes and add `--allow-prod` only after local verification. The VPS automation manifest runs the guarded production refresh once daily.
  - `import-robloxden-free-items.py` refreshes RobloxDen-discovered candidate rows in the same catalog table through `npm run import:free-item-candidates`. It resolves managed development by default and refuses other Supabase targets unless `ALLOW_PROD_FREE_ITEMS_IMPORT=true`; candidate rows are not public until the Roblox verification collector approves them. The import tolerates per-item Roblox enrichment failures so discovery can still finish; use `ROBLOXDEN_SKIP_FAVORITE_BACKFILL=true` when only candidate IDs are needed before the unified verification pass. The VPS manifest schedules this discovery pass 30 minutes before verification so Roblox throttling can settle.
  - `set-free-items-main-only.ts` keeps `/catalog/free-roblox-items` as the only published `catalog_pages` row in this route family by unpublishing slash-based category/subcategory rows. It is dry-run by default and uses the same guarded production flag.
  - `seed-catalog-pages.ts` upserts reviewed broad `/catalog` page `final.json` rows into managed-development `catalog_pages`; use `--dry-run` before writing and `--draft` when pages should stay unpublished. Content rows should be managed-development imports first, not schema migrations.
- `collections/`: game-specific `/wiki/<game>/<collection>` dataset validation, image wiring, and page seeding.
  - `collect-grow-a-garden-images.ts`, `collect-grow-a-garden-2-images.mjs`, and `collect-slime-rng-data.ts` are game collection dataset/image collectors. They write local game data/assets and do not belong to the global Roblox catalog pipeline.
  - `plan-game-collection-refresh.ts` resolves exact-collection, one-game, or all-games collection maintenance scope from registered config plus unregistered v2 collection-shaped candidates. It is read-only unless `--output` is supplied, in which case it writes only a resumable manifest under the requested path. Use `npm run plan:game-collection-refresh`.
  - `export-game-collection-final.ts` reads one existing `wiki_collection_pages` row into the approved content-workspace `final.json` shape so maintenance can preserve current copy before a writing pass. It never writes to Supabase, refuses remote reads unless `--allow-remote-read` is explicit, and refuses to overwrite files unless `--force` is explicit. Use `npm run export:game-collection-final`.
  - `register-game-collection.ts` safely adds a collection slug to an existing `GAME_COLLECTION_GROUPS` game entry. Use `npm run register:game-collection -- --game <game-slug> --collection <collection-slug> --dry-run` first. If the game group is missing, it prints the manual group block instead of editing.
  - `migrate-game-collection-datasets-v2.ts` migrates registered game collection datasets into the separated v2 shape. Public game facts live in `items[].item`; Bloxodes system fields live in `items[].system` as only `slug`, `section`, `sortOrder`, and `image`. Use `npm run migrate:game-collection-datasets:v2` for dry-run, then add `-- --apply` only after the dry-run has no blocking issues.
  - `audit-game-collection-datasets-v2.ts` is the required guard for collection datasets and the generic renderer. Use `npm run audit:game-collection-datasets:v2`; it fails on bare arrays, non-v2 datasets, dev/source/raw fields in public item data, display fields that are not public item fields, unsupported system keys, and old renderer override maps.
  - `check-game-collection-data.ts` validates local game collection datasets before writing page copy: registered config, item rows, section field/counts, useful card fields, card summaries, local image paths, and optional `description_json` section-key matches. Use it before final writing and it is also called by `verify-game-collection-finals`.
  - `collect-collection-images.ts` downloads item images from a manifest into `apps/web/public/<Game>/<Collection>` and can update matching dataset `image` fields. Use `--dry-run` first and prefer clean item/wiki images over edited thumbnails.
  - `seed-game-collection-pages.ts` upserts local game dataset collection copy into managed-development `wiki_collection_pages`; use `--dry-run` before writing and `--draft` when pages should stay unpublished. Pass `--final-json-root tmp/content-workspace/<game-slug>/collections` when approved per-page `final.json` files should override generated copy during workstation review/import. The script accepts both the new game-first `<collection-slug>/final.json` layout and older `<catalog-code>/final.json` folders.
  - `seed-game-wiki-pages.ts` upserts game hub rows into managed-development `wiki_pages`, including `description_md`, and links them to matching `roblox_universes`; use `--dry-run` before writing and `--draft` when pages should stay unpublished. Pass `--final-json-root tmp/content-workspace/<game-slug>` when an approved wiki `final.json` should override hard-coded copy during workstation review/import.
  - Both seed scripts accept `--game <slug>` for narrow production publishes. Collection seeding also accepts `--collection <slug>` for single-page retries.
  - For production runs, use `NODE_ENV=production` plus `--allow-prod` only after a clean production dry-run. Confirm the scripts are targeting the production Supabase host, not managed development.
  - For wiki/collection production publishes, confirm the production `roblox_universes` row exists first. If it is missing, collect/import/enrich the universe before seeding `wiki_pages` or `wiki_collection_pages`.
  - Before writing production wiki/collection rows, read existing production `wiki_pages` and `wiki_collection_pages` rows for the target game/code so you know whether this is a create or update and can catch duplicates or wrong slugs.
  - Publish game wiki/collection pages in order: universe first when needed, `seed-game-wiki-pages` second, production wiki readback third, `seed-game-collection-pages` last so collection rows can link to the production `wiki_page_id`.
  - After DB publish, push/deploy only the current game's repo artifacts required by the pages: `data/<Game>/`, `apps/web/public/<Game>/`, game dataset config/rendering code, and approved seed-script changes for that game. Do not include unrelated docs, other game data, temporary workspace files, or unrelated code in the game release commit.
  - Do not manually enqueue revalidation by default after wiki/collection production publishes. The app/database revalidation path should handle it; poll live pages for up to 5 minutes, then inspect the queue/worker if pages are still stale.
  - A wiki/collection production publish is not complete until the live production wiki and collection URLs return 200 and render the expected title, content, data, and images. If live routes or images 404, check whether the production deploy includes the route/config changes, `data/<Game>/`, and `apps/web/public/<Game>/`.
  - Scripts that match against `roblox_universes` must page through production rows explicitly; do not assume the default Supabase result limit is enough.
  - Keep reusable seed/upsert scripts for repeated wiki/collection work. Delete temporary collector/import scripts after their data is stable and committed.
- `articles/`: article discovery, generation, and queue lifecycle jobs.
  - `discover-article-topics.ts` collects recent Roblox leads from first-party RSS feeds, sitemaps, and direct landing pages for Pro Game Guides, Destructoid, Beebom, Sportskeeda, Game8, Game Rant, and TechWiser. Every source uses the same 18-hour default window, and `--max-age-hours` must stay below 24. It excludes obvious codes articles, requires a parseable source date, deduplicates by canonical source URL, and prints per-source funnel counts for raw, stale, malformed, excluded, duplicate, capped, and eligible rows. It fetches only eligible article pages directly to retain useful H2/H3 headings and a bounded source excerpt; no crawling API is used. `--apply` inserts new candidates, refreshes reusable source provenance, and requeues old-prompt or materially changed retryable decisions in managed dev. It requires `ARTICLE_DEV_SUPABASE_*`, accepts only an HTTPS `*.supabase.co` managed project, rejects production and localhost targets, and never writes generation jobs.
  - `curate-article-topics.ts` claims at most 12 managed-dev discovery candidates by default and sends public source leads, bounded page evidence, plus intent-matched published Bloxodes page titles from the GET-only production editorial inventory endpoint to Groq Llama JSON mode. It turns update/patch-note leads into zero or more source-supported focused guides, tier lists, or explainers, so one source URL may support several distinct topic keys. Local validation requires interchangeable search intent before grouping publishers, while same-game/different-task angles remain separate; production coverage is relevant only for the same player task, not merely the same game. Prompt upgrades selectively re-curate prior thin/evidence/overlap rejects and approved rows that ended skipped or failed, without reopening deliberate codes/collection/event exclusions. The inventory payload is capped and Groq output tokens scale with batch size to stay beneath free-tier TPM limits. Three consecutive current-prompt runs with zero approvals are marked degraded and return non-zero so systemd exposes the condition. `GROQ_API_KEY` is required.
  - `list-article-queue.ts` is the read-only input path for the article workflow runner. It lists only Groq-curated `agent_runner` rows, defaults to pending work ordered by newest source publication time, and supports JSON output for agent selection.
  - `list-article-release-review.ts` lists only managed-dev `completed` `agent_runner` rows and returns their localhost preview URLs, result paths, queue IDs, and source provenance for human publication review.
  - `update-article-queue-item.ts` is the guarded lifecycle writer for managed-dev `agent_runner` rows. Article workflow runners mark a selected row `processing`, then `completed` only after local verification and rendered browser preview; temporary operational/evidence failures become retryable `blocked` rows, while duplicate or unsuitable leads become terminal `skipped`. Human review moves completed rows to `published` only after exact production verification or to `rejected` with a reason. Completed updates require an existing, parseable `final.json`, and published updates require the exact canonical production URL.
  - `run-local-article-writer.ts` powers `npm run articles:writer:homelab`. It claims one managed-dev curated row with compare-and-set locking, maps only managed-dev credentials into the Grok child, pins `grok-4.5` by default, and always invokes Grok with automatic tool approval so systemd runs cannot pause for permission prompts. It closes the managed-dev row only after the final file and matching draft `articles` row are verified. Production overlap is available only through the GET-only editorial inventory endpoint. It is dry-run by default; `--apply` is required to claim and write. Failed or blocked jobs back off and retry up to the configured limit.
  - `run-homelab-article-batch.ts` powers `npm run articles:writer:batch`. It first returns due `blocked` rows to pending within the configured attempt limit, skips Grok when no pending rows exist, and starts one `grok-4.5 --always-approve` parent run for at most six accepted articles. The existing workflow runner owns queue lifecycle and fans research, mandatory image discovery, and writing out to subagents. It maps only managed-dev credentials into Grok, shares the single-writer lock with the one-row wrapper, and is dry-run by default. A non-empty Grok batch that exits without completing any managed-dev article returns non-zero as degraded.
  - `check-homelab-article-automation.ts` performs read-only readiness checks for the managed-dev schema, production inventory, Groq key, Grok CLI, and Chrome/Chromium. The checked-in systemd units under `scripts/ops/systemd/` schedule discovery at four fixed six-hour intervals and trigger the capped Grok batch only after successful discovery and curation; there is no separate writer timer.
  - `install-homelab-article-automation.sh` installs those units plus a `root:teja` mode-`0640` placeholder env file only when the checkout is at `/home/teja/projects/Bloxodes`. The article credential resolver automatically uses that conventional homelab path when it is readable and no explicit dev credentials are present, allowing trusted interactive `teja` runs without repository-local secrets. The installer explicitly disables the discovery timer; activation remains a separate step after readiness and Grok authentication pass.
- `content/`: local content QA helpers.
  - `check-public-copy.ts` blocks self-referential public copy such as `Use the X catalog`, `this catalog`, `dataset`, and `Bloxodes`, weak field-command copy such as `Read category first`, and AI-ish contrast filler such as `not just`; run it against generated `final.json` files before managed-development import.
  - Article writing is owned by `.agents/skills/bloxodes-article-workflow-runner`: research subagent → parent brief approval → mandatory separate `bloxodes-article-images` pass → image readiness approval → **writing subagent** (`bloxodes-article-writing`, `bloxodes-tech-article-writing`, or `bloxodes-tier-list-writing`) → parent review → `verify:article-finals`.
  - Article media: optional perfect-match YouTube uses `{{ youtube: URL_or_id }}`. Every article requires sibling `media.json`, at least one planned useful target, Supabase-hosted WebP objects for verified source images, and an expected/found/uploaded/inserted readiness check. Body images may be omitted only when reliable exact-match searches are documented and every target is explicitly accepted missing. Do not hotlink source CDNs or add article-owned source images to the repository.
  - Article structured blocks use fenced `tier-list` and `article-checklist` YAML in `content_md`. `check-article-media.ts` validates their schemas, tier detail sections, exact local files, alt text, and rendered image claims.
  - `collect-article-images.ts` reads one approved `media.json`, performs a read-only plan by default, and with `--apply` downloads exact-match verified images, converts them to WebP, uploads them to the configured Supabase Storage target, verifies public readback, and updates upload fields in the manifest. Production requires `NODE_ENV=production` plus `--allow-prod`.
  - `check-article-image-readiness.ts` reconciles expected, verified, uploaded, inserted, missing, and accepted-missing counts and checks that each hosted visual sits in its planned article section.
  - `sync-article-image-provenance.ts` reads an approved `media.json` and idempotently inserts or updates `article_source_images` for an article already imported into the target environment. It is dry-run by default; production writes require `NODE_ENV=production`, `--allow-prod`, and `--apply`.
  - `save-article-image.ts` is the legacy local-file helper. Do not use it for new article-owned source images; the current workflow uses `collect:article-images` and Supabase Storage.
  - `check-article-media.ts` validates YouTube directives, structured article blocks, and hosted image paths/alt text; used by `verify-article-finals`.
  - Game collection writing is owned by `.agents/skills/bloxodes-game-collection-workflow-runner`: collection subagent (research → data → images) → parent approval at each gate → **writing subagent** (`bloxodes-game-collection-writing`) → parent review → `verify:game-collection-finals`.
  - `import-tool-finals.ts` upserts reviewed tool `final.json` files into `tools`. Use `--dry-run` first. Workstation writes use managed Supabase development; production writes require both `NODE_ENV=production` and `--allow-prod`, then verify the saved rows through Supabase readback.
  - `import-content-final.ts` upserts reviewed article, checklist, and quiz `final.json` files into Supabase. Article imports write only to the `articles` table, including `content_md`, `faq_json`, tags, sources, and metadata. They pick a random author when missing, create an edited 16:9 cover from the linked Roblox universe thumbnail when no cover image is provided, and inject the feature image before the first H2 like generated articles. Production article imports require `SUPABASE_MEDIA_PUBLIC_URL=https://media.bloxodes.com`, refuse missing/local feature media, then read back the saved row and make one HTTP request to its cover. After article imports, verify both `/articles` and `/articles/<slug>` show the same title, author, and cover from the saved article row. It targets managed development by default and refuses production writes unless `NODE_ENV=production` is paired with `--allow-prod`.
  - `verify-article-finals.ts` is the batch verifier for reviewed article `final.json` files. Start or reuse the local web server first, then run `npm run verify:article-finals -- --base-url http://localhost:<port> --file <final.json> [...]`. It requires and validates sibling `media.json` for every article, parses finals, runs YouTube/image and copy checks, imports locally, syncs `article_source_images` provenance, reads back `articles` rows, verifies each `/articles/<slug>` route returns 200, and confirms embeds/images render when claimed.
  - `verify-engagement-finals.ts` verifies checklist and quiz `final.json` files through the same managed-development-first path: copy check, `import-content-final`, table readback, and `/checklists/<slug>` or `/quizzes/<code>` route checks.
  - `verify-wiki-final.ts`, `verify-game-collection-finals.ts`, and `verify-catalog-finals.ts` wrap the approved seed scripts with copy checks, managed-development table readback, and route checks before Browser preview. Game collection verification also runs `check:game-collection-data` for every collection before seeding.

## Operational Expectations

- Quality scripts may write only ignored reports under `tmp/test-reports/`. `validate:published-content` is read-only and defaults to managed development; other database targets require explicit `--allow-remote-read`. `verify:postdeploy` is read-only but requires an explicit HTTP target.

- Treat scripts as data pipelines: know whether the job reads only, mutates Supabase, writes local files, calls external APIs, or triggers revalidation.
- If a script creates or updates publishable content, review `/api/revalidate` coverage and any relevant Supabase revalidation trigger flow.
- If a job becomes part of the normal workflow, add a package script and update `agents/scripts/agents.md`.
- Scheduled production jobs that do not need GitHub checkout state should run through the VPS stats worker and stay manual-only in GitHub Actions. Keep Draft Code Page Generation and Discover Beebom Code Pages scheduled in GitHub unless the product direction changes.
- VPS jobs use the private `supabase_default` network and `http://supabase-kong:8000`. Keep the self-hosted Kong `rest-v1` service `read_timeout` at `300000` milliseconds so database RPCs with a 240-second statement timeout are not cut off by Kong's 60-second default.
- Keep editorial page slugs separate from stats slugs. `roblox_universes.slug` belongs to `/stats/games/*`; scripts must not copy it into `code_pages.slug`, `wiki_pages.slug`, `events_pages.slug`, `checklist_pages.slug`, `quiz_pages.code`, or `wiki_collection_pages.wiki_slug`.

## Script Authoring Checklist

1. Put the file in the correct folder.
2. Reuse a helper from `scripts/shared/` or `apps/web/src/lib/*` if one already exists.
3. Add a `package.json` command if people will run it regularly.
4. Document the script in `agents/scripts/agents.md`.
